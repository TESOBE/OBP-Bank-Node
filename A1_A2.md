# OBP Bank Node — A1 & A2 (Bank-Facing Interfaces)

This document covers **only the two interfaces the bank's CBS interacts
with**: `A1` (outbound payments — bank calls the Bank Node) and `A2` (inbound
credits — Bank Node calls the bank). The three "northbound" interfaces
(`B` OBP API, `C` RabbitMQ, `D` Cardano) are operated by the Bank Node on
the bank's behalf and need no CBS development.

For the full five-interface picture, see [`INTERFACES.md`](INTERFACES.md).

---

## A1 — Outbound payments (CBS → Bank Node)

The Bank Node exposes one HTTP listener on `localhost`. The bank's CBS calls
four endpoints under the `/obp-bank-node/v5.1.0/` prefix. All four use
`Authorization: Bearer <local_secret>` (rotate on first run; never leaves
the bank's host).

**URLs are deliberately short.** One Bank Node serves exactly one bank, so
the CBS does not pass `bank_id`, `account_id`, or `view_id` on the URL —
the Bank Node knows its own bank from config and resolves the settlement
account from `value.currency` in the request body. The **request body**
stays byte-for-byte OBP-shaped so banks already familiar with OBP can reuse
their existing payload validators.

### A1.1 Initiate a payment

```
POST http://local-node:8088/obp-bank-node/v5.1.0/transaction-requests
Authorization: Bearer <local_secret>
Content-Type: application/json
```

Request body:

```json
{
  "value": {
    "currency": "KES",
    "amount":   "1500.00"
  },
  "description": "Invoice 4471",
  "to": {
    "otherBankRoutingScheme":     "BIC",
    "otherBankRoutingAddress":    "KCBLKENXXXX",
    "otherAccountRoutingScheme":  "IBAN",
    "otherAccountRoutingAddress": "GB29NWBK60161331926819"
  },
  "charge_policy": "SHARED"
}
```

Response — HTTP `202 Accepted`:

```json
{
  "transaction_request_id": "tr-abc-123",
  "type":                   "SIMPLE",
  "from": {
    "bank_id":    "ke.01.kcs",
    "account_id": "7bc9a8e4-5d02-40e3-b129-1c3bf89de9f1"
  },
  "to": {
    "otherBankRoutingScheme":     "BIC",
    "otherBankRoutingAddress":    "KCBLKENXXXX",
    "otherAccountRoutingScheme":  "IBAN",
    "otherAccountRoutingAddress": "GB29NWBK60161331926819"
  },
  "value": {
    "currency": "KES",
    "amount":   "1500.00"
  },
  "description":   "Invoice 4471",
  "charge_policy": "SHARED",
  "status":        "INITIATED",
  "promise_id":         null,
  "promise_blockchain": null,
  "start_date":         "2026-05-09T10:30:00Z",
  "challenge":          null
}
```

The 202 is synchronous and returned in milliseconds. The Bank Node persists
the request to its local outbox before any external call, so the 202 is
durable even if the network drops immediately afterwards.

The four `to.*` routing fields are **inline** — no counterparty
pre-registration. Pick whichever scheme fits the beneficiary (BIC+IBAN,
MOBILE_PHONE, OBP, BANK_ID+ACCOUNT_ID, etc. — full list in
`BANK_INTEGRATION.md`).

`challenge` is always `null` — SCA is the bank's responsibility before this
call. The Bank Node never triggers a challenge flow.

### A1.2 Query a payment

```
GET http://local-node:8088/obp-bank-node/v5.1.0/transaction-requests/{transaction_request_id}
Authorization: Bearer <local_secret>
```

Response — HTTP `200 OK`:

```json
{
  "transaction_request_id": "tr-abc-123",
  "status":                 "COMPLETED",
  "promise_id":             "<cardano tx hash>",
  "promise_blockchain":     "Cardano",
  "netting_snapshot_id":    "snap-3a4b5c6d-7e8f-9a0b-1c2d-3e4f5a6b7c8d",
  "netting_blockchain":     "Cardano",
  "settlement_id":          "<cardano tx hash>",
  "settlement_system":      "Cardano",
  "created_at":             "2026-05-09T10:30:00Z",
  "settled_at":             "2026-05-09T10:45:12Z"
}
```

Status values progress as:

`INITIATED` → `SUBMITTED` → `PROMISE_WRITTEN` → `PENDING_NETTING` →
`PENDING_SETTLEMENT` → `COMPLETED`

Terminal failure status: `EXCEPTION`.

### A1.3 List recent payments

```
GET http://local-node:8088/obp-bank-node/v5.1.0/transaction-requests
Authorization: Bearer <local_secret>
```

Response — HTTP `200 OK`:

```json
[
  { "transaction_request_id": "tr-abc-123", "status": "COMPLETED",         "created_at": "2026-05-09T10:30:00Z" },
  { "transaction_request_id": "tr-def-456", "status": "PENDING_SETTLEMENT", "created_at": "2026-05-09T11:02:18Z" }
]
```

Convenience endpoint — banks typically know each `transaction_request_id`
from the 202 returned at POST time and prefer single-id status lookups.

### A1.4 Health (no auth)

```
GET http://local-node:8088/health
GET http://local-node:8088/obp-bank-node/v5.1.0/health
```

Response — HTTP `200 OK`:

```json
{
  "status":    "healthy",
  "service":   "OBP-Bank-Node",
  "version":   "0.1.0",
  "blockchain": "cardano",
  "timestamp": "2026-05-09T10:30:00Z"
}
```

### A1 — Error responses

| HTTP | Error code                   | Meaning                                                  |
| ---- | ---------------------------- | -------------------------------------------------------- |
| 400  | `OBP-10001`                  | Malformed JSON or missing required field                 |
| 400  | `OBP-40008`                  | Amount is zero or negative                               |
| 400  | `OBP-40003`                  | Currency mismatch with the sending account               |
| 401  | `OBP-BANK-NODE-AUTH-001`     | Missing / invalid `Authorization` header                 |
| 422  | `OBP-BANK-NODE-ROUTING-001`  | Routing address could not be resolved to an OBP API counterparty |
| 503  | `OBP-BANK-NODE-PLATFORM-001` | OBP API unreachable — instruction queued in local outbox |

A 503 with `OBP-BANK-NODE-PLATFORM-001` does **not** mean the payment is
lost. The outbox holds the instruction and submits it when connectivity
returns. The `transaction_request_id` returned in the prior 202 remains
queryable.

## A2 — Inbound credits (Bank Node → CBS)

The bank picks **one** delivery mode at config time. Every inbound credit
is delivered in that mode — the choice is per-bank, not per-payment.

The semantic payload is the same across all four modes:

```json
{
  "transaction_request_id": "tr-abc-123",
  "netting_snapshot_id":    "snap-3a4b5c6d-7e8f-9a0b-1c2d-3e4f5a6b7c8d",
  "type":                   "SIMPLE",
  "from": {
    "bank_id":      "gh.29.uk",
    "bank_routing": { "scheme": "BIC",  "address": "BARCGB22XXX" }
  },
  "to": {
    "bank_id":         "ke.01.kcs",
    "account_id":      "7bc9a8e4-5d02-40e3-b129-1c3bf89de9f1",
    "account_routing": { "scheme": "IBAN", "address": "KE12KCBL0000001234567890" }
  },
  "value": {
    "currency": "KES",
    "amount":   "1500.00"
  },
  "description":        "Invoice 4471",
  "value_date":         "2026-05-09",
  "charge_policy":      "SHARED",
  "promise_id":         "<cardano tx hash>",
  "promise_blockchain": "Cardano"
}
```

### A2 Mode 1 — `webhook_obp` (recommended)

The bank exposes one HTTPS endpoint. The Bank Node POSTs each credit to it.

```
POST <your CBS URL>
Authorization: Bearer <shared_secret>
Content-Type:  application/json

{ ...payload above... }
```

Expected response — HTTP `200 OK`:

```json
{
  "status":        "ACCEPTED",
  "cbs_reference": "CBS-TXN-20260509-98765"
}
```

Any non-2xx or timeout triggers retry with exponential backoff for 24 hours.

### A2 Mode 2 — `webhook_iso20022`

Same as Mode 1, but the request body is an ISO 20022 **camt.054** JSON
envelope (`BkToCstmrDbtCdtNtfctn`). Pick this if the CBS team already
speaks ISO 20022.

### A2 Mode 3 — `database`

Zero HTTP development on the bank side. The Bank Node `INSERT`s into a
Postgres staging table on the bank's network. The CBS polls and processes.

Schema (auto-created by the Bank Node on first connection):

```sql
CREATE TABLE obp_credit_instructions (
    transaction_request_id  VARCHAR PRIMARY KEY,
    netting_snapshot_id     VARCHAR,
    to_account_id           VARCHAR NOT NULL,
    currency                CHAR(3) NOT NULL,
    amount                  NUMERIC(18,5) NOT NULL,
    description             VARCHAR,
    value_date              DATE,
    promise_id              VARCHAR,
    promise_blockchain      VARCHAR,
    status                  VARCHAR NOT NULL DEFAULT 'PENDING',
    cbs_reference           VARCHAR,
    created_at              TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    processed_at            TIMESTAMPTZ
);
```

CBS work loop:

1. `SELECT … WHERE status = 'PENDING'`
2. Post the credit on the bank's books
3. `UPDATE … SET status = 'PROCESSED', cbs_reference = ?, processed_at = NOW()`

### A2 Mode 4 — `file`

Works with any CBS — no HTTP, no DB. The Bank Node writes
`{transaction_request_id}.json` (or `.csv`) into a shared inbound directory.
The CBS picks the file up, processes it, and writes an acknowledgement file
into a separate acknowledgement directory.

## Network requirements (firewall / ports)

Everything the bank's network team needs to allow. **All connections are
outbound from the bank's network** — no inbound ports are opened to the
public internet.

| Direction | Destination                                 | Port           | Protocol           | Purpose                                              |
| --------- | ------------------------------------------- | -------------- | ------------------ | ---------------------------------------------------- |
| Outbound  | OBP API (TESOBE-hosted)                     | 443            | HTTPS              | Interface B — submit Transaction Requests, OAuth2    |
| Outbound  | RabbitMQ (TESOBE-hosted)                    | 5671           | AMQP over TLS      | Interface C — receive credits, snapshots, settlements |
| Outbound  | Cardano node — **local** (co-located)       | 1337           | WebSocket (Ogmios) | Interface D — write Promise / Settlement / Exception |
| Outbound  | Cardano node — **managed** (Demeter, etc.)  | 443            | WebSocket over TLS | Interface D — if not co-locating cardano-node        |

The CBS reaches the Bank Node over `localhost` only — no firewall rule
required there, no public listener exposed.

The bank's TLS interception / corporate proxy (if any) needs to allow
WebSocket upgrades on the Ogmios port and persistent AMQP-over-TLS
connections on 5671.
