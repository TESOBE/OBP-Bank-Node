# OBP Bank Node — A1 & A2 (Bank-Facing Interfaces)

## A1 — Outbound payments (CBS → Bank Node)

The Bank Node exposes one HTTPS listener on `localhost`. The bank's CBS
calls four endpoints under the `/obp-bank-node/v5.1.0/` prefix.

### A1.1 Initiate a payment

```
POST https://local-node:8088/obp-bank-node/v5.1.0/transaction-requests
Authorization: Bearer <access_token>
PSD2-CERT:     <client cert PEM>
Content-Type:  application/json
```

Request body:

```json
{
  "value": {
    "currency": "KES",
    "amount":   "1500.00"
  },
  "description": "Invoice 4471",
  "to": {
    "other_bank_routing_scheme":     "BIC",
    "other_bank_routing_address":    "NWBKGB2LXXX",
    "other_account_routing_scheme":  "IBAN",
    "other_account_routing_address": "GB29NWBK60161331926819"
  },
  "originator": {
    "name":    "Acme Coffee Ltd",
    "address": "12 Market Street, Nairobi, Kenya",
    "account_routing": {
      "scheme":  "IBAN",
      "address": "KE12KCBL0000009876543210"
    }
  }
}
```

The `originator` carries FATF Recommendation 16 ("Travel Rule") information about the actual payer upstream of the bank's settlement account — i.e. the bank's customer on whose behalf the payment is being made.

Response — HTTP `202 Accepted`:

```json
{
  "transaction_request_id": "tr-abc-123",
  "type":                   "OPEN_CORRIDOR",
  "from": {
    "bank_id":    "ke.01.kcs",
    "account_id": "7bc9a8e4-5d02-40e3-b129-1c3bf89de9f1"
  },
  "to": {
    "other_bank_routing_scheme":     "BIC",
    "other_bank_routing_address":    "NWBKGB2LXXX",
    "other_account_routing_scheme":  "IBAN",
    "other_account_routing_address": "GB29NWBK60161331926819"
  },
  "originator": {
    "name":    "Acme Coffee Ltd",
    "address": "12 Market Street, Nairobi, Kenya",
    "account_routing": {
      "scheme":  "IBAN",
      "address": "KE12KCBL0000009876543210"
    },
    "source":  "explicit"
  },
  "value": {
    "currency": "KES",
    "amount":   "1500.00"
  },
  "description":   "Invoice 4471",
  "status":        "INITIATED",
  "promise_id":         null,
  "promise_blockchain": null,
  "start_date":         "2026-05-09T10:30:00Z",
  "challenge":          null
}
```

`challenge` is always `null` — SCA is the bank's responsibility before this
call. The Bank Node never triggers a challenge flow.

#### 

### A1.2 Query a payment

```
GET https://local-node:8088/obp-bank-node/v5.1.0/transaction-requests/{transaction_request_id}
Authorization: Bearer <access_token>
PSD2-CERT:     <client cert PEM>
```

Response — HTTP `200 OK`:

```json
{
  "transaction_request_id": "tr-abc-123",
  "status":                 "COMPLETED",
  "promise_id":             "<cardano tx hash>",
  "promise_blockchain":     "Cardano",
  "created_at":             "2026-05-09T10:30:00Z",
  "completed_at":           "2026-05-09T10:45:12Z"
}
```

Status values progress as:

`INITIATED` → `SUBMITTED` → `PROMISE_WRITTEN` → `PENDING_NETTING` →
`PENDING_SETTLEMENT` → `COMPLETED`

Terminal failure status: `EXCEPTION`.

### A1.3 List recent payments

```
GET https://local-node:8088/obp-bank-node/v5.1.0/transaction-requests
Authorization: Bearer <access_token>
PSD2-CERT:     <client cert PEM>
```

Response — HTTP `200 OK`:

```json
[
  { "transaction_request_id": "tr-abc-123", "status": "COMPLETED",         "created_at": "2026-05-09T10:30:00Z" },
  { "transaction_request_id": "tr-def-456", "status": "PENDING_SETTLEMENT", "created_at": "2026-05-09T11:02:18Z" }
]
```

Convenience endpoint — banks typically know each `transaction_request_id`
from the 202 returned at POST time and prefer single-id status lookups.

### A1.4 Health (no auth)

```
GET https://local-node:8088/health
GET https://local-node:8088/obp-bank-node/v5.1.0/health
```

Response — HTTP `200 OK`:

```json
{
  "status":    "healthy",
  "service":   "OBP-Bank-Node",
  "version":   "0.1.0",
  "blockchain": "cardano",
  "timestamp": "2026-05-09T10:30:00Z"
}
```

### A1 — Error responses

| HTTP | Error code                     | Meaning                                                                                  |
| ---- | ------------------------------ | ---------------------------------------------------------------------------------------- |
| 400  | `OBP-10001`                    | Malformed JSON or missing required field                                                 |
| 400  | `OBP-40008`                    | Amount is zero or negative                                                               |
| 400  | `OBP-40003`                    | Currency mismatch with the sending account                                               |
| 400  | `OBP-BANK-NODE-ORIGINATOR-001` | `originator` block missing or has an empty `name`, `address`, or `account_routing` field |
| 401  | `OBP-20202`                    | Access token missing or cannot be verified                                               |
| 401  | `OBP-20210`                    | `PSD2-CERT` does not match the certificate pinned to this consumer                       |
| 422  | `OBP-BANK-NODE-ROUTING-001`    | Routing address could not be resolved to an OBP API counterparty                         |
| 503  | `OBP-BANK-NODE-PLATFORM-001`   | OBP API unreachable — instruction queued in local outbox                                 |

A 503 with `OBP-BANK-NODE-PLATFORM-001` does **not** mean the payment is
lost. The outbox holds the instruction and submits it when connectivity
returns. The `transaction_request_id` returned in the prior 202 remains
queryable.

## A2 — Inbound credits (Bank Node → CBS)

The bank picks **one** delivery mode at config time. Every inbound credit
is delivered in that mode — the choice is per-bank, not per-payment.

The semantic data delivered to the CBS is the same shape across both modes
— Mode 1 wraps it as camt.054, Mode 2 writes it verbatim:

```json
{
  "transaction_request_id": "tr-abc-123",
  "from": {
    "bank_routing": { "scheme": "BIC", "address": "BARCGB22XXX" }
  },
  "to": {
    "account_routing": { "scheme": "IBAN", "address": "KE12KCBL0000001234567890" }
  },
  "originator": {
    "name":    "Acme Coffee Ltd",
    "address": "12 Market Street, Nairobi, Kenya",
    "account_routing": { "scheme": "IBAN", "address": "KE12KCBL0000009876543210" }
  },
  "value": {
    "currency": "KES",
    "amount":   "1500.00"
  },
  "description":        "Invoice 4471",
  "value_date":         "2026-05-09",
  "promise_id":         "<cardano tx hash>",
  "promise_blockchain": "Cardano"
}
```

The `originator` block is always present on A2 deliveries — it propagates
the FATF Travel Rule data the sending bank supplied on its A1.1 call. The
receiving CBS should record this against the incoming credit for its own
AML / reporting obligations.

### A2 Mode 1 — `webhook_iso20022`

The bank exposes one HTTPS endpoint. The Bank Node POSTs each credit to it
encoded as an ISO 20022 **camt.054** JSON envelope
(`BkToCstmrDbtCdtNtfctn`) — the same notification format banks already
receive from correspondents over SWIFT, so the CBS-side parser is usually
already in place.

The bank decides how to secure the endpoint — the Bank Node can be
configured at onboarding to present any of:

- a client certificate (sent as `PSD2-CERT: <PEM>` header, or via
  transport-layer mTLS),
- a static bearer token (`Authorization: Bearer <token>` issued by the
  bank),
- an OAuth 2.0 `client_credentials` exchange against a bank-provided token
  endpoint (Bank Node then sends `Authorization: Bearer <access_token>` on
  the webhook call),
- an IP allow-list with no in-band credentials.

```
POST <your CBS URL>
Authorization: Bearer <token>
PSD2-CERT:     <Bank Node cert PEM>
Content-Type:  application/json
```

```json
{
  "BkToCstmrDbtCdtNtfctn": {
    "GrpHdr": {
      "MsgId":   "tr-abc-123",
      "CreDtTm": "2026-05-09T10:45:12Z"
    },
    "Ntfctn": [{
      "Id":      "tr-abc-123",
      "CreDtTm": "2026-05-09T10:45:12Z",
      "Acct":    { "Id": { "IBAN": "KE12KCBL0000001234567890" } },
      "Ntry": [{
        "Amt":       { "Ccy": "KES", "value": "1500.00" },
        "CdtDbtInd": "CRDT",
        "Sts":       { "Cd": "BOOK" },
        "BookgDt":   { "Dt": "2026-05-09" },
        "ValDt":     { "Dt": "2026-05-09" },
        "NtryDtls": [{
          "TxDtls": [{
            "Refs":      { "EndToEndId": "tr-abc-123" },
            "RltdPties": {
              "Dbtr":     { "Pty": {
                "Nm":      "Acme Coffee Ltd",
                "PstlAdr": { "AdrLine": ["12 Market Street, Nairobi, Kenya"] }
              }},
              "DbtrAcct": { "Id": { "IBAN": "KE12KCBL0000009876543210" } },
              "DbtrAgt":  { "FinInstnId": { "BICFI": "BARCGB22XXX" } }
            },
            "RmtInf": { "Ustrd": ["Invoice 4471"] }
          }]
        }],
        "AddtlNtryInf": "promise_id=<cardano tx hash>; promise_blockchain=Cardano"
      }]
    }]
  }
}
```

Expected response — HTTP `200 OK`:

```json
{
  "status":        "ACCEPTED",
  "cbs_reference": "CBS-TXN-20260509-98765"
}
```

Any non-2xx or timeout triggers retry with exponential backoff.

### A2 Mode 2 — `file`

For banks who wish. The Bank Node
writes `{transaction_request_id}.json` (the payload above, verbatim) into a
shared inbound directory; the CBS picks it up, processes it, and writes an
acknowledgement file into a separate directory.

## Network requirements (firewall / ports)

The VM where the OBP-Bank-Node runs needs the following. All connections
are outbound from the bank's network — no inbound ports are opened to the
public internet.

| Direction | Destination                                            | Port                            | Protocol        | Purpose                                                               |
| --------- | ------------------------------------------------------ | ------------------------------- | --------------- | --------------------------------------------------------------------- |
| Outbound  | OBP API (TESOBE-hosted)                                | 443                             | HTTPS           | Interface B — submit Transaction Requests, OAuth2                     |
| Outbound  | RabbitMQ (TESOBE-hosted)                               | 5671                            | AMQP over TLS   | Interface C — receive credits, snapshots, settlements                 |
| Outbound  | Cardano peer relays (per `cardano-node` topology file) | 3001 (typical, varies per peer) | TCP — Ouroboros | Interface D — chain sync, Promise / Settlement / Exception submission |

The OBP-Bank-Node ↔ Ogmios connection runs on `localhost:1337` and is
loopback on the same VM; no firewall rule required.

The CBS reaches the Bank Node over `localhost` only — no firewall rule
required there, no public listener exposed.

The bank's corporate proxy (if any) needs to allow:

- persistent AMQP-over-TLS connections on 5671,
- plain outbound TCP to Cardano peer addresses on the ports named in the
  `cardano-node` topology file (Cardano P2P uses Ouroboros framing, not
  TLS, so TLS-interception proxies do not apply — but proxies that block
  non-TLS egress on non-standard ports will need explicit allow-listing).

# Appendix — Internal design notes

What the Bank Node does internally after receiving an A1.1 request — which
OBP API endpoints (Interface B) and Cardano writes (Interface D) get
triggered, and in what order.

## Failure handling

| Failure point                                                                        | Behaviour                                                                                                                                        |
| ------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| Outbox write fails (step 5)                                                          | Respond `500`. The CBS retries the call.                                                                                                         |
| OBP API unreachable (step 6)                                                         | Leave the outbox row at `INITIATED` with `last_attempted_at` timestamp; retry with exponential backoff. The CBS sees the latest status via A1.2. |
| OBP API rejects the Transaction Request (step 6, e.g. unroutable destination)        | Mark outbox row `EXCEPTION`; write a Cardano Exception record on Interface D. The CBS sees `status: EXCEPTION` via A1.2.                         |
| Cardano unreachable (step 7)                                                         | Retry; status stays at `SUBMITTED` until Cardano accepts.                                                                                        |
| Destination bank rejects asynchronously (later, via Interface C `obp_status_update`) | Update local status to `EXCEPTION`; write a Cardano Exception record on Interface D. The CBS sees `status: EXCEPTION` via A1.2.                  |

## 

What happens after A1.1 (`POST /transaction-requests`)

| #   | When                     | Action                                                                                                                | OBP API endpoint (Interface B)                                                                                                    | Cardano action (Interface D)                         | Status after        |
| --- | ------------------------ | --------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------- | ------------------- |
| 1   | sync                     | Validate Bearer token and match `PSD2-CERT` against the pinned consumer cert                                          | —                                                                                                                                 | —                                                    | — (401 on failure)  |
| 2   | sync                     | Parse + validate JSON body (currency, positive amount, all four `to.*`, all three `originator.*`)                     | —                                                                                                                                 | —                                                    | — (400 on failure)  |
| 3   | sync                     | Resolve `value.currency` → bank's configured settlement account                                                       | —                                                                                                                                 | —                                                    | — (422 if no match) |
| 4   | sync                     | Mint a new `transaction_request_id` (UUID v4)                                                                         | —                                                                                                                                 | —                                                    | —                   |
| 5   | sync                     | `INSERT` outbox row with the request payload                                                                          | —                                                                                                                                 | —                                                    | `INITIATED`         |
| →   | **respond `202` to CBS** | —                                                                                                                     | —                                                                                                                                 | —                                                    | —                   |
| 6   | async                    | Submit the OBP OPEN_CORRIDOR Transaction Request (inline routing + originator — the OBP API resolves the destination) | `POST /obp/v7.0.0/banks/{bank_id}/accounts/{account_id}/views/owner/transaction-request-types/OPEN_CORRIDOR/transaction-requests` | —                                                    | `SUBMITTED`         |
| 7   | async                    | Build, sign, and submit a Cardano Promise (metadata-only tx)                                                          | —                                                                                                                                 | Ogmios `submitTransaction` (JSON-RPC over WebSocket) | `PROMISE_WRITTEN`   |

The `{account_id}` in step 6's URL is the bank's **settlement account at
OBP-API** — its nostro / operating position within the Open Corridor system,
not a customer account. The bank's CBS handles customer ledgers internally;
OBP-API only tracks the bank's net interbank position. The Bank Node
resolves it at step 3 from `value.currency` via its `bank` config block; TESOBE
provisions this settlement account when the bank is onboarded. For multi-currency
banks, this becomes a per-currency map (see open question 3 below).

Later lifecycle states (`PENDING_NETTING` → `PENDING_SETTLEMENT` → `COMPLETED`, or terminal `EXCEPTION`) are driven by **inbound messages on
Interface C**, not by A1.1 itself — those are documented separately.

## Open design questions

These are not yet decided — flag in code reviews / PRs as they come up:

1. **Order of OBP submission vs Cardano Promise write.** Current narrative
   in `TLDR.md` writes the Promise *after* the OBP submission (steps 6
   then 7). Alternative: write the Promise first as a local commitment,
   then submit to OBP. Trade-off is which side is the source of truth if
   one fails.
2. **Outbox replay loop semantics.** Tick-based worker that polls
   `INITIATED` rows, or event-driven (resumed when connectivity recovers)?
   Affects latency-after-recovery.
3. **`from.account_id` for multi-currency banks.** Current `BankConfig`
   has a single `account_id`. For banks with separate settlement accounts
   per currency, this needs to become a map. Affects step 3.
